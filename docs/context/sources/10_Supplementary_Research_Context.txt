# 1. Literature Review Map


## 1.1. Rate Limiting Fundamentals


Rate limiting là cơ chế kiểm soát số lượng request mà một client có thể gửi tới hệ thống trong một khoảng thời gian nhất định.


Mục tiêu:


- bảo vệ backend khỏi traffic quá tải;
- đảm bảo công bằng giữa các user;
- duy trì ổn định hệ thống;
- kiểm soát việc sử dụng tài nguyên.


Trong hệ thống đơn instance, rate limiter có thể lưu trạng thái trong memory.


Ví dụ:


```
User A


Request Count:
80 / 100


Window:
1 minute
```


Tuy nhiên khi hệ thống mở rộng thành nhiều instance, trạng thái rate limit cần được chia sẻ.


---


# 1.2. Rate Limiting Algorithms


## Fixed Window Counter


Ý tưởng:


Chia thời gian thành các khoảng cố định.


Ví dụ:


```
100 requests / minute


10:00:00 - 10:00:59
```


Ưu điểm:


- đơn giản;
- dễ triển khai;
- hiệu năng tốt.


Nhược điểm:


- boundary problem.


Ví dụ:


```
10:00:59


100 requests




10:01:00


100 requests
```


Trong thời gian rất ngắn có thể xảy ra 200 request.


---


## Sliding Window


Ý tưởng:


Xem xét một khoảng thời gian trượt liên tục.


Ví dụ:


```
Last 60 seconds
```


Ưu điểm:


- chính xác hơn Fixed Window;
- giảm burst tại boundary.


Nhược điểm:


- cần nhiều trạng thái hơn;
- chi phí xử lý cao hơn.


---


## Token Bucket


Ý tưởng:


Bucket chứa token được refill theo tốc độ cố định.


Ví dụ:


```
Capacity:
100 tokens


Refill:
10 tokens/sec
```


Mỗi request cần lấy token.


Ưu điểm:


- hỗ trợ burst traffic;
- phù hợp nhiều hệ thống thực tế.


Nhược điểm:


- cần quản lý trạng thái bucket;
- phức tạp hơn Fixed Window.

```
 requests: 80,

```


---


# 5.3. Atomic Operation


Vấn đề:


Nhiều request cùng cập nhật counter.


Ví dụ:


```
Request A


read count = 99




Request B


read count = 99
```


Nếu không atomic:


```
Both accepted


Actual count = 101
```


Giải pháp:


Redis Lua Script hoặc atomic command.


Mục tiêu nghiên cứu:


```
Does atomic operation reduce overshoot?
```
