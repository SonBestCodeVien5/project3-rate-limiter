The run used two API instances, Redis Fixed Window (`Q=20`, `W=1000ms`), five legitimate clients, a constrained backend (capacity 4, 50ms service), 100 total/20 legitimate RPS, 30 seconds per run, 200 max in-flight, 2s request timeout, and fail-open/fail-closed. For each policy, a healthy 30-second baseline ran first. The runner fixed recovery threshold at 1.5 × that baseline's legitimate successful-request p95 before starting its matching outage case: 81.2371ms for open and 80.9740ms for closed. Redis pause began at about t=4s and lasted 2.004s after `pause_completed`; requested/completed control-plane transitions are recorded individually.

All four runs scheduled and sent 3,000/3,000 requests with zero generator drops, 100 total RPS and 20 legitimate RPS. P95 schedule lag was 1.24–1.27ms. The largest wall/monotonic schedule and response-latency residuals were 0.102ms and 0.101ms. API request/decision counters, API backend attempts/confirmed arrivals, backend arrival/outcome counters, and HTTP summary counts reconciled in every case. Runtime image inspection completed before each load. No Redis limiter errors appeared in healthy baselines; during outage, open recorded 230 fail-open and closed 231 fail-closed decisions as expected.

The analyzer recorded first legitimate post-unpause success at 57.7ms (open) and 125.6ms (closed), while stable recovery remained `inconclusive` for both policies. There were 23 full one-second candidate windows after unpause, but none met the clean-window condition: each window had unsuccessful legitimate responses and backend 5xx overload outcomes. The healthy baselines also had 257/260 backend overloads and only 538/600 and 533/600 legitimate successes (open/closed), so this mixed offered load did not provide an error-free healthy state for stable recovery calibration. Legitimate successful-request p95 in the first post-unpause windows stayed below the preselected thresholds; latency alone did not satisfy recovery. Do not report first success as stable recovery or interpret this inconclusive result as recovery failure under other loads.

During the outage phase, legitimate availability by send-time phase was open: before 82.7%, pausing 77.8%, outage 45.0%, unpausing 42.9%, after 86.6%; closed: before 90.1%, pausing 62.5%, outage 0%, unpausing 12.5%, after 90.1%.
