# Tick-rate follow-up v3 (corrected kernel formula)

This addendum supersedes the rate equation and numerical prediction in `FOLLOWUP.md` (v2). V1 README/archive and v2 worklog/archive/checksums remain untouched. The main archived observation remains the same, captured at revision `60f7dd63cddcc0fcd0889dbe961483634d9a169c`; no live observer, compilation, service query, or clock change was performed for this correction.

The earlier v2 estimate incorrectly multiplied the normalized tick by the frequency ratio. The Microsoft WSL rolling kernel source instead computes `second_length = tick_usec * 1000 * USER_HZ`, then adds `ntp_tick_adj` and `time_freq` before scaling. Under a simplified model that omits the internal `ntp_tick_adj` and clocksource-specific terms, this means the normalized MONOTONIC/RAW ratio is approximately:

`tick_usec / nominal_USER_HZ_tick + frequency_ppm / 1,000,000`

The read-only C and Python `adjtimex(modes=0)` queries reported `tick_us=9167` and `frequency=-33.5937805 ppm`. Runtime `getconf CLK_TCK` reports USER_HZ=100; kernel `CONFIG_HZ=250` is the scheduler tick rate, not USER_HZ. Thus the additive estimate is `9167/10000 - 33.5937805/1,000,000 = 0.916666406219`. The observed ratio from the existing 1,792 samples is `89.972190856 / 98.151508971 = 0.916666404819`. The difference is about `1.40e-9` in the ratio, or 0.137 microseconds over the observed RAW interval. This close fit strongly supports the nonstandard tick as the rate parameter behind the continuous MONOTONIC/RAW divergence. It is not an exact-kernel proof: the running image identifies as 6.18.54.1, while the source inspected is Microsoft’s rolling `linux-msft-wsl-6.18.y` branch; internal tick and clocksource correction terms were not separately observed.

MONOTONIC_RAW stayed smooth across all three realtime events, running at a nearly constant rate relative to MONOTONIC before and after each. The discrete realtime advances of about 2.95 seconds occurred relative to both clocks. Adjacent timesyncd packet-count increments and reported offsets closely matched those wall advances. This supports timesyncd as the likely wall-correction actor, with the tick-related rate mismatch as a plausible reason for the recurring offset; no writer syscall was traced. The process that set `ADJ_TICK=9167` remains unknown. `systemd-timesyncd` v255 source does not use `ADJ_TICK`, and `auditctl`/`ausearch` were unavailable to inspect pre-existing NTP_TICK audit records.

The temporary proposed diagnostic remains unperformed: after re-confirming USER_HZ=100 and with explicit approval, set only `ADJ_TICK` to 10,000 µs, capture/query the state, then rollback only `ADJ_TICK` to its observed original 9,167 µs. This requires `CAP_SYS_TIME`, changes a global timebase, and is not asserted as a fix. Frequency and service configuration would not be changed.

Sources: Microsoft WSL rolling kernel [`kernel/time/ntp.c`](https://github.com/microsoft/WSL2-Linux-Kernel/blob/linux-msft-wsl-6.18.y/kernel/time/ntp.c) documents the additive `tick_usec`, `ntp_tick_adj`, `time_freq` calculation and `ADJ_TICK` update; exact running tag not verified. Linux UAPI [`timex.h`](https://github.com/torvalds/linux/blob/master/include/uapi/linux/timex.h) defines `tick` and `ADJ_TICK`. Installed systemd version is 255.4; [`timesyncd-manager.c` v255](https://github.com/systemd/systemd/blob/v255/src/timesync/timesyncd-manager.c) uses offset correction modes and not `ADJ_TICK`. See also [`time(7)`](https://man7.org/linux/man-pages/man7/time.7.html) for USER_HZ and scheduler HZ distinction, and [`adjtimex(2)`](https://man7.org/linux/man-pages/man2/adjtimex.2.html) for permissions.
