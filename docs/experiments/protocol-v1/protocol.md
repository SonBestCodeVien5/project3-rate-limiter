## Order, gates, and stopping

The manifest fixes one SHA-256-sorted permutation of the 42 normal/burst/mixed/scaling cells, repeated unchanged in each of three blocks. The four outage cells follow each block in this order: open healthy, open outage, closed healthy, closed outage. For each outage policy, the existing runner must pass its healthy gate before its matching pause. No cells run concurrently. After each case, preserve the full artifacts and wait for the owned Compose project to be absent before proceeding. Preserve all failed, interrupted, and replacement attempts; never overwrite an attempt or change a threshold after viewing results.

The tooling-validity gates are fixed:

- Full source revision and clean checkout match; recorded server policy and resolved topology match the manifest; state reset is true; all expected API instances and backend settings are present. Store run IDs, image fingerprints, host/runtime, commands, actual start/end times, and all artifacts.
- Every scheduled trace row is retained; request IDs are unique within a run; `scheduled` equals trace row count; `sent + generator_dropped = scheduled`; zero generator drops are allowed for a valid run. Analyzer summary/trace counts must reconcile.
- Measure actual sent rate separately for each traffic class and phase relative to recorded run start. It must be within ±5% of its target. Burst targets are legitimate 20 and abusive 20 RPS in [0,2), legitimate 20 and abusive 200 RPS in [2,4), and legitimate 20 and abusive 20 RPS in [4,30). Normal is 20 legitimate RPS; mixed is 20 legitimate plus 100 abusive RPS; scaling is all legitimate at the cell’s target rate. For outage, apply class-rate fidelity to each entire healthy/outage offered-load run (20 legitimate + 80 abusive RPS); the shorter outage event phases are used for availability/fallback reporting, not separate ±5% rate gates. For each nonzero target class/phase, p95 schedule lag must be ≤ min(10 ms, 1000/target-RPS ms). Compare wall-time scheduling and response residuals against monotonic trace measurements; maximum residual must be ≤5 ms.
- API request totals equal sent requests; API rejects equal HTTP 429; API/backend confirmed arrivals reconcile with the trace and summary; backend arrivals equal success + overload + canceled. No healthy Redis limiter errors are allowed. All runs need analyzer output and the existing per-run evidence. Normal cells also require no 429 and no backend overload. Intended overload in burst/mixed or expected fallback/5xx during a Redis outage are outcomes to report, not automatically tooling failures.
- For each outage healthy baseline, the runner’s stop gate requires every legitimate request to succeed, zero generator drops, zero transport errors/timeouts, zero limiter/API limiter errors, and zero backend overload. If it fails, its corresponding outage is not run. Pause requested/completed and unpause requested/completed UTC event records must be ordered; report requested and completed times separately. A two-second sleep is not itself a measured two-second outage.

A tooling-gate failure invalidates that attempt, not its raw evidence. Preserve it and its reason, then use only the bounded same-config replacement allowance. After the allowance is exhausted, stop that cell and report it unmeasured. A failed host clock/observer gate stops the sequence. A backend overload in the mixed/burst cases or a fail-policy outcome during outage is not by itself a tooling-gate failure. Keep correctness-oracle status separate: an FW `inconclusive` result is not a correctness pass, and an observed violation remains reportable.

## Redis resource and network semantics

For non-outage cells, record the Redis sampler log. The analyzer reports `network_input_bytes_delta`, `network_output_bytes_delta`, and the corresponding bytes/second using cumulative Redis counters from the first to last valid sampled timestamp; record that actual interval. These are bytes and bytes/second over the sampled interval, not full-run totals, not limiter-only traffic, not bytes/request, and not wire/packet overhead. They include limiter traffic, `INFO cpu`/`memory`/`stats`, healthchecks, and administrative boundary queries. Stage 1 saw five complete samples at 2.29–2.42 second intervals despite a one-second sleep, because three Compose exec/INFO calls dominate each loop. Its single 20-RPS paired run recorded 844 B/s output with sampling off and 2,059 B/s with sampling on. Treat this only as evidence of sampler/admin contamination; do not apply a correction factor or infer a latency/performance winner. There was no paired incremental CPU-cost estimate.

If any sample lacks a network counter, the corresponding result is `incomplete` with null delta/rate. If observed counters decrease, report `inconclusive` with null delta/rate. A reset between two observed samples may be hidden. Never impute missing values. No Redis resource sampler runs during outage because blocked INFO calls would interfere with fault timing; outage cells therefore have no Redis CPU, memory, or network result.
