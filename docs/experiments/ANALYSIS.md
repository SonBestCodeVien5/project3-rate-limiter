# Trace analysis contract

`python3 scripts/analyze.py CASE_DIR` reads `CASE_DIR/policy.json`, `CASE_DIR/load/metadata.json`, `CASE_DIR/load/summary.json`, and `CASE_DIR/load/requests.jsonl`. It writes `analysis.json` and `analysis.md` beside the policy. It exits nonzero for malformed required evidence, summary counts that disagree with raw rows, or a conflict between workload labels and the recorded policy. An inconclusive oracle or an observed violation is a successful analysis with an explicit status, not a process error. `outage-events.txt`, backend/API counter snapshots, and `redis-resources.log` are optional. No raw artifact is rewritten.

The runner records actual server configuration in `policy.json` with `schema_version: 1`, `mode` (`none`, `local`, `redis`), `algorithm` (`fixed-window`, `token-bucket`), positive `limit`, `window_ms`, `capacity`, `rate_per_sec`, nonempty `namespace`, Boolean `state_reset`, and `fail_policy` (`open`, `closed`). `state_reset: true` asserts a fresh namespace or fresh local processes before the entire traced workload. Load generator mode/algorithm/fail policy values are labels, not proof of server state. The runner should record a policy even for mode `none`; its algorithm numbers are configuration context and the oracle is not applicable.

Each JSONL row uses the load generator's request ID, client key and class, scheduled/sent/end timestamps, latency, HTTP status, timeout/error, limiter decision and server decision timestamp, and instance. Missing `sent_at` means the generator dropped the request before sending. A timeout or missing response header may have changed limiter state, so it prevents an exact replay for that key. The trace requires unique request IDs and explicit timezone offsets. Decisions are grouped by server `decision_at`; client send order never supplies concurrent decision order.

For Fixed Window, epoch aligned windows group `allow` and `reject` by client key and, in local mode, instance. `max(0, observed allows - limit)` is a **lower bound** on overshoot, even in a partial window. Client trace timestamps do not establish a complete server-clock observation interval, so all windows remain labelled incomplete. Fresh, isolated initial state plus a complete raw trace can still check the decisions *observed* in a partial window: the allow count must equal `min(observed requests, limit)`. A missing decision, fallback, unknown instance, outage, canceled run, or absent reset makes that scope's check inconclusive. Local instance quotas are checked separately; the global accepted count against one shared quota is reported as an observed comparison, not as a local implementation error.

For Token Bucket, the analyzer replays full capacity and refill at `rate_per_sec` using server millisecond timestamps. Decisions sharing one millisecond are compared as a batch: their allowable count is `min(batch size, floor(tokens))`, avoiding arbitrary tie order. Replay is inconclusive if initial state is unknown, the run was canceled, raw/summary counts disagree, there is an outage, or a sent request for that key has missing/fallback evidence. An accepted count above `capacity + rate × observed interval` is independently reported as an envelope violation; a global single-bucket envelope is also shown for local mode. A Fixed Window quota is never applied to Token Bucket.

If `outage-events.txt` has the four ordered UTC events `pause_requested`, `pause_completed`, `unpause_requested`, and `unpause_completed`, the analyzer keeps transition intervals separate. Availability is legitimate HTTP 2xx successes divided by legitimate **sent** requests in each phase, grouped by `sent_at`. Fallback decisions are also grouped by server decision time. First legitimate post-unpause success is only a functional observation. Stable recovery requires consecutive full, clean windows with enough legitimate samples, no fallback/error, and p95 below an explicit threshold. The full-window boundary is capped at `summary.started_at + metadata.config.duration_ns`; response drain cannot extend offered-load coverage. Configure `--recovery-p95-ms N`, `--recovery-window-ms N` (default 1000), `--recovery-min-samples N` (default 5), and `--recovery-consecutive N` (default 3). Without a latency threshold or sufficient windows, stable recovery is `null` and inconclusive. Pilot validation must choose these values before formal measurements.

`backend-before.json`/`backend-after.json` and corresponding API snapshots provide counter deltas when present. Redis `INFO stats` resource samples include cumulative `total_net_input_bytes` and `total_net_output_bytes`; the analyzer reports first-to-last nonnegative byte deltas and bytes/second when timestamps span positive time. Missing counters in any sample mark that direction incomplete; a decrease between observed samples (for example after Redis restart) makes its delta/rate inconclusive. A reset between samples can still go undetected. These are total Redis TCP protocol bytes observed by Redis, including sampler/admin commands such as `INFO`, not limiter-only bytes/request or wire/packet overhead. Redis resource output reports memory snapshots and CPU seconds divided by elapsed seconds as average **CPU cores**, not whole-machine CPU percentage. Missing evidence produces `null` or an inconclusive field. Exact Token Bucket replay assumes server time does not step backward within a run; the trace lacks a serial decision sequence to diagnose a backward clock step. The analysis describes observations from one run; repetitions, load fidelity, confounders, and uncertainty across runs remain part of the later evaluation protocol.
