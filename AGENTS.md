## Delegation workflow

Honor explicit user requests for root-only work or no delegation; root performs that authorized scope personally. Otherwise root coordinates and integrates, then dispatches the next ready scoped package within the user's active scope, subject to task dependencies, stop points and experiment gates. Do not dispatch new work after a requested planning-only or stopping boundary. For substantive scoped work under this default delegation policy, automatically delegate to `gpt-6-luna`, `reasoning_effort=low`, `fork_turns=none`, using the runtime's actual available slots (one worker by default, at most three independent workers). Never ask a worker to spawn. If model/tool/slot unavailable, report that limitation; do not silently use a stronger root model for substantive work. Reuse a worker with `followup_task` for the same scope; use one fresh Luna for a distinct scope, without uncontrolled retry/respawn loops.

Assign non-overlapping file ownership and a concrete package. Give each worker only the relevant paths and small context. Do not forward full conversation history. Worker performs implementation and necessary focused checks. Root does not duplicate implementation, tests or review by default; inspect concise completion/blocker reports and resolve concrete integration conflicts. Wait for completion notifications; do not list/poll agent status or send routine progress queries. Respect higher-priority runtime wait and user communication limits.

Worker handoff (English; root replies to the user in Vietnamese): task IDs; changed files/result paths; checks performed and failures/skips; limitations and next prerequisite. For measurement, also include revision, config, artifact paths and checksums. No raw logs/traces in chat; inspect only a named finding when needed. Inspect relevant code before proposing or changing it.

## Documentation language and reader workflow

- Human-facing documentation uses Vietnamese for titles, explanations, status updates, tables and command comments. This includes `README.md`, the [reader index](docs/README.md), current planning/report/design/demo guides and the experiment/tool guides listed in that index. Do not append English progress paragraphs to Vietnamese documents. Use the reader index glossary as an explanation guide, not a mandatory translation rule: keep familiar technical terms such as atomic/atomicity/non-atomic, rate limiter, quota, request, client, API instance, local/shared state, workload, burst, concurrent, scaling, baseline, pilot, calibration, benchmark, offered load, runner, analyzer, exporter, artifact, manifest, trace, revision, working tree, fingerprint, fail-open/fail-closed, first success/stable recovery, inconclusive, and observed_violations in English where they read naturally. Keep natural Vietnamese terms such as độ trễ, thông lượng, bộ nhớ, bộ đếm, bằng chứng, cấu hình, lượt chạy, and yêu cầu kỹ thuật. A glossary English headword with a clear Vietnamese explanation does not require replacing that English term in prose. Distinguish worker slots (concurrent agent capacity) from measurement slots (planned run positions); distinguish pain point (business difficulty) from bottleneck (technical point of congestion). Preserve product/algorithm names, paths, commands, flags, API/JSON fields, metric identifiers, run IDs, revisions, hashes and source titles verbatim.
- Agent instructions/prompts, `AGENTS.md`, `.agents/`, `docs/context/PROJECT_BRIEF.md`, `docs/context/SESSION_CHECKPOINT.md`, archival/datestamped worklogs and machine artifacts may remain English. Label English agent handoff/resumption blocks within human-facing documents so the reader can skip them. The source notes in `docs/context/sources/` and `SOURCE_INDEX.md` follow the existing Drive sync rules; do not rewrite them merely for language consistency.
- Maintain `docs/README.md` as the human entrypoint: first reading, task-based routes, report-section mapping, terminology and historical/agent-only exclusions. Keep `README.md` linked to it. When adding or retiring a reader-facing document, update the index. Prefer links and explicit historical labels over renaming/moving evidence or duplicating current status across files.
- Current guides must distinguish current state from dated historical evidence, and link to `REMAINING_WORK_PLAN.md` for task state and `experiments/PROTOCOL_READINESS.md` for measurement gates. Correct stale opening claims when touching a guide; preserve the dated record and all limitations. Documentation changes do not authorize load, experiments or T10 analysis.
- Report material follows business problem → pain point → impact → technical requirement → solution → experiment → evaluation → future work. Distinguish requirements, engineering choices and optional future work. Keep hypothetical impact separate from measured outcomes, pilot separate from formal evidence, data completeness separate from correctness, and inconclusive separate from pass. Trace results to protocol/manifest, revision, run/cell, artifacts and limitations; leave unperformed analysis explicitly pending.
- Translation must preserve every numerical value, unit, threshold, negation, uncertainty, authorization boundary and evidence identifier. Never translate or edit locked `docs/experiments/protocol-v*/` files, raw evidence, checksums or archived reports in place for readability. Add a Vietnamese explanation with a source link in the current guides instead.
- Commit translations by independently reviewable reader topic (planning/report; technical/measurement/demo); commit navigation/documentation policy separately, and checkpoint/progress updates separately. Inspect each staged diff, check whitespace and local links, and verify preserved commands/identifiers. Documentation-only changes need no code suite or live rerun.

## Commit discipline

Use one independently reviewable feature or fix per commit, together with its directly related tests and documentation. Split independent changes even when they touch the same file. Commit measurement evidence separately from code changes, and commit progress/checkpoint updates separately from both.

Inspect the staged diff before every commit and stage explicit files or hunks; do not bundle the whole worktree. At the requested stopping point, update the checkpoint and leave the worktree clean without deleting user changes or ignored raw artifacts. Preserve recorded measurement revisions and evidence when reorganizing commits.
